# QuantPulse Data Model

## Status

**Initial design**

The QuantPulse data model is intentionally **not finalized**.

The system is expected to evolve as market-data ingestion, quantitative research, analytics, portfolio management, and backtesting requirements become clearer.

This document defines the current conceptual model and design principles rather than committing the project to a final database schema.

---

# 1. Objectives

The data model should eventually support:

- Market-data ingestion
- Financial instrument metadata
- Historical and real-time market data
- Quantitative analytics
- Portfolio management
- Research experiments
- Backtesting
- Reproducible research
- Analytics and model results

The initial design prioritizes **flexibility and clear domain boundaries** over premature schema optimization.

---

# 2. Main Data Domains

The following domains are currently planned:

- **User**
- **Instrument**
- **Market Data**
- **Trade**
- **Quote**
- **Order Book**
- **Analytics Result**
- **Portfolio**
- **Research Experiment**
- **Backtest**

These represent conceptual domains rather than finalized collections, tables, or classes.

The exact relationships between these domains will be refined as the application develops.

---

# 4. User

A `User` represents an application user.

Potential responsibilities include:

- Authentication and authorization
- Portfolio ownership
- Research ownership
- Backtest ownership
- User-specific application preferences

Potential fields may eventually include:

```text
user_id
email
created_at
updated_at
```

The exact user schema will depend on the authentication and application architecture.

---

# 5. Instrument

An `Instrument` represents a financial asset or tradable security.

Examples may include:

- Equities
- ETFs
- Futures
- Options
- Forex pairs
- Cryptocurrencies
- Indices

Potential fields include:

```text
instrument_id
symbol
exchange
asset_type
currency
```

Additional identifiers may eventually be required to uniquely identify instruments across exchanges and data providers.

The project should avoid assuming that `symbol` alone is globally unique.

For example:

```text
symbol + exchange
```

may be insufficient for some asset classes, so a provider-specific or globally recognized identifier may eventually be required.

---

# 6. Market Data

Market data represents observations received from market-data providers or generated by market-data processing pipelines.

Potential fields include:

```text
instrument_id
exchange
timestamp
price
quantity
bid
ask
volume
```

Depending on the data source, market data may eventually be represented through more specific domains such as:

- Trades
- Quotes
- Candles/OHLCV
- Order-book snapshots
- Order-book updates
- Aggregated market data

The exact schema will be determined after implementing and evaluating the first market-data ingestion pipeline.

---

# 7. Trade

A `Trade` represents an executed transaction.

Potential fields include:

```text
instrument_id
exchange
timestamp
price
quantity
trade_id
```

Additional fields may eventually include:

```text
side
trade_type
source
sequence_number
```

The meaning and availability of these fields will depend on the market-data provider.

Trade data should preserve sufficient information to support future research into:

- Trade volume
- Trade imbalance
- Price impact
- Execution analysis
- Intraday analytics

---

# 8. Quote

A `Quote` represents bid and ask information for an instrument at a specific point in time.

Potential fields include:

```text
instrument_id
exchange
timestamp
bid
ask
bid_quantity
ask_quantity
```

Quotes may be used to calculate metrics such as:

- Bid-ask spread
- Mid price
- Relative spread
- Quote imbalance
- Liquidity measures

---

# 9. Order Book

An `Order Book` represents available buy and sell liquidity at different price levels.

A conceptual representation may contain:

```text
instrument_id
exchange
timestamp

bids:
    price
    quantity

asks:
    price
    quantity
```

The final representation may distinguish between:

- Full order-book snapshots
- Incremental updates
- Level 1 data
- Level 2 data
- Level 3/order-level data

Storage requirements are expected to differ significantly depending on the selected market-data depth.

---

# 10. Analytics Result

An `Analytics Result` represents the output of a quantitative calculation.

Examples include:

- Mean
- Median
- Variance
- Volatility
- Correlation
- Sharpe ratio
- Maximum drawdown
- VWAP
- Order imbalance

A conceptual result may contain:

```text
instrument_id
model
timestamp
value
parameters
```

The final structure should also allow the system to identify:

- Which model produced the result
- Which input data was used
- Which parameters were used
- Which version of the model was used
- When the calculation was performed

This is important for reproducibility.

---

# 11. Portfolio

A `Portfolio` represents a collection of financial positions associated with a user.

Potential concepts include:

```text

user_id
name
base_currency
created_at
updated_at
```

A portfolio may eventually contain:

```text
positions
transactions
cash
portfolio_value
```

The final model will depend on whether QuantPulse supports only research portfolios or also live/paper trading workflows.

# 12. Research Experiment

A `Research Experiment` represents a reproducible quantitative research process.

Potential fields include:


# 15. Database Strategy

## 15.1 Application Data

**MongoDB** is currently planned for application-oriented data such as:

- User data
- Portfolio information
- Research metadata
- Analytics metadata
- Backtest metadata
- Configuration data

MongoDB provides flexibility while the domain model is still evolving.

---

## 15.2 Market Data

High-volume market data presents different requirements from ordinary application data.

Potential concerns include:

- Very high write volume
- Large historical datasets
- Time-based queries
- Instrument-based queries
- Retention policies
- Compression
- Sequential ingestion
- Historical replay
- Query latency

For this reason, the final storage technology for high-volume time-series market data has **not yet been finalized**.

Possible approaches will be evaluated through benchmarking rather than selected prematurely.

---

# 16. Time-Series Considerations

Market data is inherently time-oriented.

Typical access patterns are expected to include:

```text
Get all observations for instrument X
between time A and time B.
```

Other common queries may include:

```text
Get the latest observation for instrument X.
```

```text
Get all trades for instrument X during a session.
```

```text
Replay market data for a backtest.
```

```text
Calculate rolling statistics over a time window.
```

The final storage design should therefore consider:

- Timestamp indexing
- Instrument indexing
- Compound indexes
- Partitioning
- Compression
- Data retention
- Historical replay performance

---

# 17. Schema Evolution

The schema is expected to change as QuantPulse develops.

Changes may include:

- Adding new fields
- Splitting a domain into separate collections
- Combining metadata structures
- Introducing new identifiers
- Changing indexing strategies
- Introducing specialized time-series storage
- Adding versioning information

Schema evolution should be treated as a normal part of development rather than avoided through premature abstraction.

---

# 18. Data Quality

Market data should not be assumed to be clean.

The eventual ingestion pipeline should consider:

- Missing observations
- Duplicate records
- Invalid timestamps
- Out-of-order events
- Invalid prices
- Invalid quantities
- Market-session boundaries
- Corporate actions
- Trading halts
- Exchange-specific conventions

Data-quality rules should be documented alongside the ingestion pipeline once the first real data source is integrated.

---

# 19. Identifiers

Identifiers should be designed carefully because financial instruments are not necessarily globally identifiable by ticker symbols.

The final model may require combinations of:

```text
internal_id
symbol
exchange
asset_type
provider
provider_id
```

The exact identifier strategy will depend on the market-data providers and asset classes supported by QuantPulse.

- Storage overhead
- Dataset size

# 21. Design Principles

## 21.1 Do Not Finalize the Schema Prematurely

Database schemas should not be finalized before the application's actual access patterns are understood.

Schema decisions should be driven by:

- Query patterns
- Write volume
- Read volume
- Data retention
- Indexing requirements
- Storage requirements
- Latency requirements

---

## 21.2 Separate Domain Concepts from Storage

A domain concept such as `Trade` should not automatically dictate a MongoDB collection, SQL table, or time-series table.

The conceptual model should describe **what the system needs to represent**.

The storage model should describe **how that information is persisted efficiently**.

These are related but separate concerns.

---

## 21.3 Optimize Based on Evidence

Storage and indexing decisions should be supported by:

- Benchmarks
- Production-like workloads
- Query profiling
- Dataset-size projections
- Ingestion tests

Premature optimization should be avoided.

---

## 21.4 Preserve Reproducibility

Research and backtesting data should eventually preserve enough metadata to reproduce analytical results.

Important metadata may include:

```text
data source
data version
time range
instrument
model
parameters
code version
execution timestamp
```

# 24. Current Scope

This document defines the **initial conceptual data model only**.

It intentionally does **not** define:

- Final MongoDB collections
- Final document structures
- SQL schemas
- Production indexes
- Sharding strategy
- Partitioning strategy
- Final time-series database
- Complete API contracts

Those decisions should be made after the first ingestion, analytics, research, and backtesting workflows provide real access-pattern and performance data.
